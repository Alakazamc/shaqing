# 模块：NPC

> 上位：`docs/SYSTEM.md` §0、`docs/modules/13-eventlines.md`（NPC 关系用事件线实现）。

## 1. 它补的是一个真实短板

现有设计里事件是自包含的，没有贯穿的人。原作也没有——它的事件都是一次性文本。

NPC 补三件事：

| 补什么 | 说明 |
|---|---|
| 连贯性 | 一条命里有反复出现的人，而不是一串互不相干的段子 |
| **反讽乘数的载体** | 你 17 岁背叛的人在 41 岁回来，死法标签与他对上，`Iro` 吃满 4.0 |
| 传播 | 关系的截图比属性的截图好转发 |

第二条最实在。`Iro`（`SYSTEM.md` §3.3）最高 4.0，是三个乘数里最大的单一杠杆，
而一个反复出现的人比一个抽象标签好用得多——玩家能讲出"这个人是谁"。

## 2. 池子大，出场少

有个张力必须先解决：NPC 状态会爆炸，而 `C1` 要求交互极简、`Q6` 要求一局 90 秒。

**解法是池大出场少：**

- NPC 池设计几十个（首发目标 30–40）
- **一局只遇到 3–5 个**，由 seed + 家庭 + 轨道决定
- 深度来自每个 NPC 有阶段推进，**不来自同时有一堆人**

这条是硬约束。同时活跃的 NPC 超过 5 个，手机竖屏放不下，且每年的文本量会撑爆时长目标。

## 3. 数据结构

```js
{
  id: 'npc_qishou',
  name: '下棋的老头',        // 可以没有真名。代称更像真实记忆
  emoji: '🧓',
  scope: 'xianxia',          // 圈层，决定他说话的语域
  seasons: [1, 2],           // 可能出场的季
  axis: 'qinmi',             // 关系轴：亲密 / 怨恨，同一根轴 -10…10
  eventline: 'el_qishou',    // 关系推进用事件线实现，见 13-eventlines.md
  tags: ['山野', '献祭'],     // 会传染给你的标签，喂反讽
  gate: 'FLAG?["f_shancun"]', // 出场门槛：状态，不是低概率随机

  // 以下三个字段不进游戏，只给写作者看
  bio: '……',
  voice: '说话短，不解释，爱用棋的比喻',
  never: '不会主动求你，不会解释自己是谁',
}
```

### 3.1 `bio` / `voice` / `never` 是连贯性的工程答案

这三个字段**不进游戏**，是给写文案的人的约束。

其中 **`never`（这个角色不会做什么）比 `bio` 有用得多**：
它防的正是十条事件写下来人物走形。`bio` 告诉你他是谁，
`never` 告诉你哪些写法是错的——后者才是可执行的。

写作时按 `never` 自查：这条事件里他做的事，有没有落在他的 `never` 里？

## 4. NPC 是人形的人设牌，但他会离开

复用现成映射（`BRIEF.md` §3）：NPC 也是被动倍率源，你不"操作"他们。

但和人设牌有一处根本不同：

| | 人设牌 | NPC |
|---|---|---|
| 增减 | 只增不减 | **会离开、会反目** |
| 波动性 | 无 | 有 |

这个波动性正好喂振幅（`SYSTEM.md` §3.1）——NPC 退场往往就是水位曲线的转折点。

## 5. 关系轴与阶段

**一根轴，不是两根。** `axis` 取值 -10…10，负数是怨恨，正数是亲密，
零是"认识但没什么"。用一根轴而不是"好感度 + 敌意度"两根，
因为两根轴会让玩家去算，违反 C1 的极简原则。

阶段推进由事件线负责（`13-eventlines.md`）：每个 NPC 一条事件线，
阶段之间有 `minGap` / `maxGap` 年间隔。超过 `maxGap` 时，带关系内容的事件线可播出一次 `missEvent`，
把“这个人淡了”写成可见后果，而不是静默消失。关系轴存于 `NPCAX[npcId].axis`（-10…10），
只有事件选项的 `relation` 改变它；事件线阶段存于同一对象的 `stage`。

## 6. 退场是重点戏

退场方式至少四种，每种都是高桥段分事件：

| 退场 | 说明 |
|---|---|
| 死亡 | 可携带死法标签，喂你的反讽 |
| 绝交 | 关系轴打到极负 |
| 失联 | 超过 `maxGap` 自然沉默的显式化 |
| **变成你的对手** | 最有戏的一种：他带着自己的轨道回来 |

按 `13-eventlines.md` §3，NPC 关系线的"淡了"必须做成**分叉**而不是截断：
继续深交与就此淡了都推进关系轴，方向不同，但都是完整的一条路。

## 7. 连贯性的真风险，以及解法

风险很具体：**NPC 设定越复杂，越容易和随机事件撞车**
——一个已经绝交的人又出现在普通事件里。

解法两条：

1. 所有 NPC 事件的 `include` 必须检查该 NPC 的 `NPCLV`（阶段）与存活状态
2. **NPC 事件不进通用加权池**，只能靠门槛进池（`noRandom: true` + 事件线驱动）

第 2 条是关键。通用池是随机的，随机就会撞车。把 NPC 事件完全移出通用池，
撞车在结构上就不可能发生，不需要靠作者小心。

## 8. DSL 命名空间新增

补进 `03-events.md` §1.4：

| 键 | 类型 | 说明 |
|---|---|---|
| `NPC` | 数组 | 当前在场的 NPC id |
| `NPCLV` | 标量 | **主导** NPC 的关系阶段。多 NPC 判定用 `NPCAX` |
| `NPCAX` | 数组 | 形如 `["npc_qishou:3"]`，供精确判定 |
| `NPCGONE` | 数组 | 已退场的 NPC id（含退场方式后缀） |
| `NPCREL` | 派生数组 | 形如 `["npc_id:axis"]`，供关系条件与调试展示 |

`NPCGONE` 单独一个键，是为了让"绝交的人不再出现"这类条件写起来短：
`NPCGONE!["npc_qishou"]`。

## 9. 一致性检查

补进 `content/README.md` §5：

1. 每个 NPC 的 `eventline` 存在，且其 `track` 与 NPC 的 `scope` 相容
2. 每个 NPC 至少有一个退场事件，且退场事件**唯一**
3. NPC 事件全部 `noRandom === true`（不进通用池）
4. 所有 NPC 事件的 `include` 都引用了 `NPC` 或 `NPCAX`
   （否则可能对已退场的 NPC 触发）
5. `bio` / `voice` / `never` 三字段非空——缺任一项视为设定不完整
6. 同一局可能同时在场的 NPC 数量上界 ≤ 5（按 `gate` 做静态可满足性估算）

## 10. 分期

**状态模型与 schema 进 A 期，内容量进 B 期。**

- A 期：NPC 状态、DSL 四个新键、事件线驱动、退场机制，内容只做 **2 个 NPC**
- B 期：铺到 30–40 个

理由与真结局进 A 期相同：schema 改动 retrofit 最贵，
会推翻已经写好的事件数据。
