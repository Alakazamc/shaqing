# 模块：场景模式（深入事件线）

> 上位：`docs/BRIEF.md` §3（小丑牌映射不得改动）、C1（交互只有点击）、
> `docs/SYSTEM.md` §1（脉冲与时长）、`docs/modules/13-eventlines.md`。

---

## 1. 要解决的问题

原作的节奏是**一件事点一下就下一年**。事件再好也只是一个孤立的段子，
玩家从不觉得自己"进入"了某件事。

本作的事件线（`13-eventlines.md`）虽然跨年，但每年只推进一个阶段，
中间隔着 1–6 年的其他内容。结果是**深度被摊薄**：
一条 4 阶段的事件线在体验上仍然是四个互不相连的瞬间。

**场景模式**让玩家在遇到关键节点时**沉进去**：
同一年内连续若干个节拍，把一件事讲完，再回到年度循环。

## 2. 场景不破坏小丑牌映射，反而让它更准

BRIEF §3 规定映射不得改动：`过完一年 = 出一手牌`。

场景**仍然发生在同一年内，仍然是一手牌**——只是这手牌的结算
从"瞬间算完"展开成"逐个节拍累加"。

这恰恰更接近小丑牌：小丑牌的爽感就在于**一手牌被逐张结算**，
数字一张一张往上爬，倍率咬合的过程是可见的。
现在的设计里"一年"是瞬间结算的，那个过程被压掉了。

| | 现在 | 加入场景后 |
|---|---|---|
| 一手牌 | 一年，瞬间结算 | 一年；关键年展开成 3–6 个节拍 |
| 数字爬升 | 一次跳到位 | 节拍逐个累加，`B` 递增，`M` 保持 |
| 连锁可见性 | 靠结算面板逐行蹦 | 靠节拍本身 |

**所以场景是在补齐映射，不是在偏离它。** 这一条很重要：
它意味着场景不需要为自己找理由，它本来就该有。

## 3. 时长代价：必须重算预算，并修正正典

这是场景模式唯一的真实代价，不能含糊。

`SYSTEM.md` §1.2 原定：总脉冲 30–45，其中决策脉冲 14–16，熟练局 100–150 秒。

若把 3–4 个决策点改造成场景、每个场景 4 个节拍，
脉冲数增加约 9–12 个：

```
原：35 脉冲 ≈ 100–150 秒
后：44 脉冲 ≈ 130–190 秒
```

### 3.1 修正方案

**不能只靠"接受变长"**，那会撞到传播阈值。采用组合方案：

| 调整项 | 原值 | 新值 |
|---|---|---|
| 决策点总数 | 14–16 | **12–14** |
| 其中场景 | — | **3–4** |
| 总脉冲 | 30–45 | **45–60** |
| 熟练局时长 | 100–150 秒 | **130–170 秒** |
| 无事件年压缩 | 一次掠过 1–3 年 | **一次掠过 1–4 年** |

减少非场景决策点是主要手段：**用更少但更深的决策，换掉更多但更浅的决策。**
这个交换本身就是设计上的改善——现在的 14–16 个决策点里，
有相当一部分是"选 A 还是选 B"的浅选择。

### 3.2 需要同步修改的正典

- `SYSTEM.md` §1.2 时长目标表（全部数字）
- `SYSTEM.md` §1.3 各季决策点数量（14–16 → 12–14 的重新分配）
- `SYSTEM.md` §8 待调参项增加"场景数与节拍数"
- `09-vertical-slice.md` §5 调参跑要新增时长分布检查

**时长必须实测**：熟练局中位数超过 170 秒即视为不达标，
优先削减非场景决策点，而不是削减场景。

## 4. 参数

| 项 | 值 | 理由 |
|---|---|---|
| 每局场景数 | **3–4** | 再多就撞时长红线 |
| 每场景节拍数 | **3–6** | 少于 3 感觉不到"进入"，多于 6 变视觉小说 |
| 其中决策节拍 | **1–2** | 其余是推进节拍 |
| 单节拍文本 | **≤ 30 字** | 比普通事件的 60 字更短，节奏要紧 |
| 单场景目标时长 | **≤ 25 秒** | |

节拍文本比普通事件短一半，这是刻意的：场景靠**密度和推进感**成立，
不靠信息量。一节拍一句话，点一下，下一句。

## 5. 哪些节点值得做成场景

场景是稀缺资源（一局只有 3–4 个），只给三类节点：

| 节点 | 理由 |
|---|---|
| **事件线入口** | 第一次进入一条线，需要建立"这件事开始了"的感觉 |
| **分叉点** | `13-eventlines.md` §3 的分叉选择，是全局最重要的决策类型之一 |
| **加码 / 收手时刻** | 见 §6 |

普通年度事件、flavor 事件、季末结算**都不做场景**。

选哪几个节点做场景由 seed 决定，但**分叉点优先**——
若本局会遇到分叉，它一定是场景之一。

## 6. 场景让真结局的那个时刻真正成立

`08-true-ending.md` §4 要求收手选项必须显示"放弃 N 分"，
让玩家**看着**那个数字点下去。

场景把这件事强化了一个量级：如果玩家已经在这个场景里点了四下、
数字一路爬到十八万，第五下才是"演还是不演"——
那么放弃的重量完全不一样。

```
节拍 1   平台的人加了你微信              +0
节拍 2   他们把数据摆出来                +2.1万
节拍 3   合同发过来了，条款很简单         +5.6万
节拍 4   你妈打电话问你最近在忙什么       +10.7万
节拍 5   ┌ 演。签了 ┐              +18.4万
         └ 不演了。回家吃饭 ┘   放弃 18.4万
```

前四个节拍不是铺垫，**它们是玩家自己一步一步爬上去的**。
第五下的放弃因此是放弃自己的劳动，不是放弃一个抽象数字。

因此：**每局至少有一个场景必须是加码/收手场景**，
且它应当落在 S4 或更晚（对应真结局条件 ④）。

## 7. 与信号层的配合

场景是信号层效果（`15-signal-fx.md`）最好的载体：
劣化可以**逐节拍加深**，而不是一次性爆发。

```
节拍 1   正常
节拍 2   第 7 个字之后开始偏色
节拍 3   色差加重，出现字符错位
节拍 4   文字破碎（A 路逐字 transform）
```

单点事件做不出这种渐进，因为它只有一屏。
`lingyi` 轨道（`04-tracks.md` §4.0）的入口与关键节点应当全部是场景。

## 8. 红线：不能变成视觉小说

这是场景模式最大的风险。一旦场景变长变多，
这个游戏就从"90 秒一局、截图即传播"变成文字冒险游戏，
`C6` 的整条传播链会断。

四条硬约束：

1. **每局场景数上限 4**，写进引擎常量，不做成内容可配
2. **单场景节拍上限 6**，`seal()` 时校验（`14-content-api.md` §3）
3. **节拍文本 ≤ 30 字**，做成自动断言
4. **不做打字机效果**。文本立即全量显示，点击立即推进，永不等待

第 4 条尤其关键。打字机是让文字游戏变慢的头号元凶，
而且它与 `15-signal-fx.md` §4 的"点击必须能打断动效"直接冲突。

## 9. 数据结构

场景是事件线的一个属性，不是新的顶层概念：

```js
// content/eventlines.js
{
  id: 'el_pingtai_jiama',
  stages: 3,
  chain: ['el_pj_s1', 'el_pj_s2', 'el_pj_s3'],
  scenes: {
    // 阶段 → 该阶段以场景形式呈现，节拍是一串事件 id
    2: { beats: ['el_pj_s2_b1', 'el_pj_s2_b2', 'el_pj_s2_b3',
                 'el_pj_s2_b4', 'el_pj_s2_b5'],
         signalRamp: null },
  },
}
```

节拍事件复用现有事件结构（`03-events.md` §2），
只是 `kind: 'beat'`，且全部 `noRandom: true`。

**因此场景不需要新的内容 schema**，只需要 `eventlines.js` 多一个 `scenes` 字段
与一个新的 `kind` 取值。这一点对 `14-content-api.md` 的纯追加原则很重要。

## 10. 一致性检查

补进 `content/README.md` §5.1：

1. 每个 `scenes[stage].beats` 内事件存在，`kind === 'beat'`，`noRandom === true`
2. `beats` 长度在 **3–6** 之间
3. 每个 beat 事件文本 **≤ 30 字**
4. 每个场景内 `kind: 'beat'` 且带 `options` 的节拍数在 **1–2** 之间
5. `scenes` 的键都落在 `1 … stages` 范围内
6. 全局：任一局可能遇到的场景数 **≤ 4**（按 `gate` 静态估算）
7. 每条带 `restraint` 选项的场景，其 `escalate` 选项与之在**同一节拍**内
   （否则"放弃 N 分"算不出来）

## 11. 分期

| 期 | 范围 |
|---|---|
| **A 期** | 场景机制、`scenes` 字段、`kind: 'beat'`、节拍内计分累加、时长实测与重调参；内容做 **2 个场景**（1 个分叉场景 + 1 个加码/收手场景） |
| **B 期** | 铺到每局 3–4 个场景、信号层逐节拍劣化、`lingyi` 轨道全场景化 |

A 期必须包含加码/收手场景，因为它是验证 §6 那个设计假设的唯一方式——
**如果场景没让"放弃"变重，那场景模式就不值得它的时长代价。**
